# Минимальные права базы «Точки дня»

Миграция `20260917110000_minimize_tochka_client_grants.sql` ограничивает только три подтверждённых клиентских объекта «Точки дня»:

- `user_app_data` — `SELECT`, `INSERT`, `UPDATE`, `DELETE` для вошедшего пользователя;
- `tochka_documents` — `SELECT`, `INSERT`, `UPDATE`, `DELETE` для вошедшего пользователя;
- `tochka_members` — `SELECT` и изменение только столбца `last_seen_at`.

Доступ к конкретным строкам по-прежнему определяют существующие RLS-политики. Роль `anon` и неявная роль `public` не получают прав на эти таблицы. Миграция не изменяет Studkab, общий `app_data`, серверные таблицы, функции, Storage и default privileges проекта.

## Совместимость

Изменение совместимо с текущим клиентом: приложение читает и сохраняет собственное состояние, управляет собственными документами и обновляет только `last_seen_at`. Edge Functions используют `service_role`; его права миграция не изменяет. `TRUNCATE`, `TRIGGER` и `REFERENCES` браузерному клиенту не требуются.

Перед production-применением в отдельном тестовом проекте необходимо проверить:

1. вход существующего пользователя;
2. загрузку и повторное чтение облачного состояния;
3. создание, скачивание и удаление документа;
4. обновление времени последнего посещения;
5. отказ анонимного запроса и отказ доступа к чужой строке.

## Откат

Если совместимость не подтвердится, сначала определить конкретную отсутствующую операцию. Предпочтительный откат — вернуть только требуемое право новой миграцией. Полное восстановление прежних избыточных прав допускается лишь как временная аварийная мера:

```sql
grant truncate, references, trigger
on table public.user_app_data, public.tochka_documents
to authenticated;
```

Роль `anon`, таблица `tochka_members`, Studkab и общий `app_data` при таком откате не изменяются.

## Отложенная настройка Auth

Supabase Advisor сообщает, что **Leaked Password Protection** отключена. Репозиторная миграция эту настройку не меняет. Её включение относится к этапу тестового проекта и принимается отдельными сценариями:

- вход с действующим паролем;
- сброс пароля по письму;
- установка нового допустимого пароля;
- понятный отказ для известного скомпрометированного пароля.

Только после успешной приёмки настройку можно отдельно включать в production.
