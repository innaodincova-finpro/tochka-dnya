# Восстановление базы «Точки дня»

Этот порядок предназначен только для нового пустого проекта Supabase. Он создаёт структуру базы, правила доступа, хранилище документов, push и Telegram-часть. Пользовательские записи и секреты в репозитории не хранятся: их восстанавливают отдельно из резервной копии проекта.

## Порядок

1. Создать новый проект Supabase и получить прямую строку подключения к Postgres.
2. Из корня репозитория выполнить:

   ```sh
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/rebuild.sql
   ```

3. Убедиться, что Cron не содержит рабочего адреса. Сразу после rebuild он
   безопасно бездействует, потому что параметр адреса не задан.
4. Задать секреты функций в настройках нового проекта. Не помещать их в GitHub
   или SQL-файлы.
5. Развернуть все 10 функций из `supabase/functions` с явным идентификатором
   нового тестового проекта. Существующий production workflow для этого не
   использовать: в нём закреплён production project ref.
6. Только после развёртывания функций задать адрес нового проекта:

   ```sql
   alter database postgres set "app.settings.tochka_functions_base_url"
     = 'https://<NEW_PROJECT_REF>.supabase.co';
   ```

   Нельзя подставлять адрес рабочего проекта при репетиции.
7. Выполнить `npm test`, затем проверить вход, сохранение одной тестовой
   записи, документ, привязку Telegram и напоминание без отправки реальным
   пользователям.

Если любая SQL-команда завершается ошибкой, выполнение останавливается. Продолжать с середины нельзя: нужно удалить тестовый проект, исправить причину и повторить на новом пустом проекте.

## Что не восстанавливает этот сценарий

- учётные записи и действующие сессии Auth;
- пользовательские записи и загруженные файлы;
- секреты Telegram, DeepSeek, VAPID и служебные ключи;
- настройки расписания, зависящие от адреса нового проекта.
- значения параметра `app.settings.tochka_functions_base_url`;
- историю production-миграций: репозиторий содержит 11 локальных файлов и
  rebuild-снимок из 22 источников, но не полную миграционную lineage; при
  read-only инвентаризации до этой интеграции в production было 37 записей.

Две локальные миграции `20260915133000` и `20260915140000` относятся к
общему production-проекту и содержат зависимости Studkab/`public.app_data`.
Они сохраняются как история, но rebuild использует их документированные
Tochka-only extracts из `supabase/recovery`.

Это данные резервной копии и конфигурация окружения, а не схема базы.

## Статус доказательств

`npm run test:recovery` восстанавливает только синтетическую PGlite-базу.
`rebuild-regression.cjs` проверяет наличие, порядок и статический состав
источников. Ни один из этих тестов не доказывает восстановление Auth,
production-строк, бинарных Storage-объектов, секретов или работу всех функций в
новом Supabase-проекте. Полное восстановление считается проверенным только после
отдельной облачной репетиции с измерением RPO/RTO.

В текущей среде отсутствовали `psql`, сервер PostgreSQL и Docker, поэтому SQL
не исполнялся на настоящем чистом PostgreSQL. Выполнена статическая проверка
порядка, наличия создаваемых таблиц и политик, provenance recovery extracts и
отсутствия mixed-project зависимостей. Это dependency validation, а не restore
test.
