# Помощник: изолированный первый этап

Основа: 5.8.13, ca04694eae174596e6f613f1fd0464f77d6a6dd1. Зафиксирована ветка backup/pre-assistant-2026-09-12. Рабочие index.html, sw.js, серверные функции и схема БД не меняются.

## Что работает
Карточка предложения для встречи, расхода и заметки, явное подтверждение/отмена, добавление только в искусственную базу в оперативной памяти. Проверяется формат, владелец тестовой записи, срок предложения, повторное применение и запрет восстановления удалённого id. Вывод текста через textContent. CSP запрещает сеть. Публичных адресов API, ключей и личных данных здесь нет.

Это НЕ подключённый ИИ: поля заполняются вручную для проверки процесса. Проверка owner в чистой функции не является серверной авторизацией. Эта версия не предназначена для личных данных.

## Запуск
Из корня репозитория: `python3 -m http.server 8765 --bind 127.0.0.1 --directory assistant-lab`, затем http://127.0.0.1:8765/. Не выкладывать под областью действия рабочего service worker; не подключать рабочий Supabase. Для тестов: `npm ci`, `node assistant-lab/test.cjs`, `npm test`.

## Следующие этапы и обязательные условия
1. Выбрать отдельный Telegram-бот для Точки дня и обработчик ИИ с лимитом расходов. Нужен доступ владельца к настройке бота/секретов; не помещать токены в HTML, GitHub или сообщения.
2. Сделать отдельный тестовый backend: аутентификация и серверная привязка Telegram id через одноразовый код из авторизованного приложения. Разрешить пилот только владельцу по серверному allowlist. Никогда не доверять owner из тела запроса или email/username Telegram.
3. Первый реальный режим — только предложения: текст/голос → модель → строгая проверка структуры → карточка, без доступа к рабочим записям. Неоднозначную дату/время уточнять. Удаление/изменение существующих записей не предоставлять модели.
4. Реальную запись проектировать через отдельную очередь предложений с идемпотентным подтверждением; не делать слепой upsert полного user_app_data. Сейчас клиент использует mergeThree и сравнение updated_at с повтором при конфликте. Продумать подтверждение из двух устройств, отмену/отзыв доступа, часовой пояс, работу офлайн и повтор webhook. Поле address в прототипе перед интеграцией сопоставить с фактическим полем события приложения.
5. Тестовый сервер/аккаунт: проверить конкурентное сохранение и повторные доставки. Локальные проверки mergeThree не доказывают безопасность серверного пути записи.
6. Перед доступом к реальным данным сделать свежий снимок, провести восстановление в изолированной среде, проверить границы доступа, включить только владельцу с выключателем. Затем проверка на реальном телефоне.

## Границы готовности
Пилот для владельца, Telegram, распознавание речи, ИИ, серверное сохранение и реальные end-to-end сценарии НЕ выполнены. Автоматические тесты текущей версии и 10 тестов контракта предложений прошли локально. Не считать этот этап готовым помощником и не сливать в production до следующих этапов.

## Серверная проверка бота, 12.09.2026
Добавлена отдельная функция `tochka-assistant-setup` (JWT gateway включён плюс проверка реального подтверждённого email владельца через Auth). Она вызывает только Telegram getMe; не отправляет сообщения, не устанавливает webhook, не обращается к записям БД и не использует service-role. При неправильном боте возвращает ошибку, токен и ответы Telegram не выводит. Имена секретов: `TOCHKA_ASSISTANT_BOT_TOKEN` и `TOCHKA_ASSISTANT_OWNER_EMAIL` (подтверждённая почта владельца приложения), хранить в Supabase Edge Functions → Secrets. Развёртывание отдельно от main: deploy_edge_function с verify_jwt=true. Это проверка подключения, НЕ обработчик сообщений и НЕ готовый ИИ.
Локально: 10 дополнительных проверок авторизации, ошибок сети, неверного бота, отсутствия/неверного формата токена. Настоящий getMe станет проверяемым после сохранения токена и запроса владельца с его пользовательской сессией; серверные админ-ключи вместо пользовательской сессии не допускаются.

Страница проверки опубликована отдельно: https://innaodincova-finpro.github.io/tochka-assistant/ (исходники публикации в корневом репозитории, папка tochka-assistant). Копия для тестов здесь в assistant-link. При изменениях синхронизировать эти три файла. Вход непосредственно в Supabase Auth, сессия в памяти и локальный logout по окончании проверки. Пароль очищается; записи приложения не читаются. CORS разрешён только для указанного origin. Проверены 5 сценариев UI в jsdom и preflight; реальный токен не подтверждён до входа владельца.
