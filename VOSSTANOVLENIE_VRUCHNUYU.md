# Ручное восстановление: учётные записи, секреты и файлы

Дата: 16 сентября 2026 года.

## Зачем этот документ

Репетиция 15 сентября ([протокол](RECOVERY_REHEARSAL_2026-09-15.md)) доказала, что база данных восстанавливается из копии без потерь. Три части облака она не охватила: учётные записи людей, закрытые ключи серверных функций и сами загруженные файлы. Полная облачная репетиция для них невозможна — она требует третьего рабочего проекта Supabase, а это платный тариф; решением владельца от 15 сентября платный тариф не подключается.

Поэтому здесь письменный порядок: что где лежит, откуда берётся и в каком порядке восстанавливается вручную. В конце — честная проверка, что из перечисленного действительно сохранено сегодня, а что нет.

Восстановление самой структуры базы описано отдельно, в [supabase/REBUILD.md](supabase/REBUILD.md). Этот документ — то, что делается после него.

---

## Часть 1. Учётные записи людей

**Что это.** Почта, подтверждение почты, зашифрованный пароль и номер каждого человека. Хранится в закрытой служебной части базы Supabase (схема `auth`). К записям людей — заметкам, событиям, финансам — эти записи привязаны номером человека.

**Откуда берётся при восстановлении.** Из копии базы, если копия снята вместе со служебной частью. Обычная выгрузка только пользовательских таблиц учётные записи не содержит.

**Порядок восстановления.**

1. Создать новый проект Supabase, выполнить `supabase/rebuild.sql` — появится структура без данных.
2. Восстановить служебную часть `auth` из копии **раньше** пользовательских таблиц. Иначе строки записей не с чем будет связать: они ссылаются на номер человека.
3. Восстановить пользовательские таблицы.
4. Проверить, что число строк в `auth.users` совпадает с числом людей в реестре приложения.

**Что нельзя восстановить и что с этим делать.** Действующие входы не переносятся: после восстановления все люди окажутся разлогинены и войдут заново по своему паролю. Записи на их телефонах при этом целы — приложение работает без сети, — и после входа сольются с облаком.

**Если копии с частью `auth` нет.** Тогда учётные записи создаются заново по обычному порядку приглашений: каждому человеку — новое приглашение, он задаёт новый пароль. Номера людей при этом изменятся, и связать восстановленные записи со старыми номерами будет нельзя. Это потеря, которую предотвращает только копия.

## Часть 2. Закрытые ключи серверных функций

Ключи делятся на три вида по тому, откуда их взять заново.

### Вид А. Лежат в самой базе — значит, есть в копии базы

| Что | Где именно | Что будет, если потерять |
|---|---|---|
| Ключ подписи уведомлений (VAPID) | таблица `push_configuration`, поле `vapid` | Функция создаст новый сама, но все подписки на уведомления перестанут работать: каждому человеку придётся заново включить уведомления |
| Закрытый ключ запуска уведомлений по расписанию | `push_configuration`, поле `cron_token` | Расписание перестанет запускаться, пока новый ключ не будет прописан в задании расписания |
| Закрытый ключ запуска Telegram-напоминаний | `tochka_telegram_reminder_config`, поле `cron_token` | То же для напоминаний |
| Отпечаток закрытого слова Telegram | `tochka_assistant_pilot`, поле `hook_hash` | Бот перестанет принимать сообщения, пока привязка не будет сделана заново |

Вывод: копия базы закрывает этот вид целиком. Отдельно хранить ничего не нужно.

### Вид Б. Выдаются сторонними службами — берутся там заново

| Что | Где взять заново |
|---|---|
| Ключ Telegram-бота (`TOCHKA_ASSISTANT_BOT_TOKEN`) | В переписке с `@BotFather` в Telegram: команда `/token`. Владелец бота — вы |
| Ключ DeepSeek (`TOCHKA_ASSISTANT_DEEPSEEK_API_KEY`) | Личный кабинет DeepSeek, раздел ключей. Старый ключ при этом лучше удалить |
| Ключ доступа для выкладки | https://supabase.com/dashboard/account/tokens — создать новый и вставить в GitHub по [инструкции выкладки](VYKLADKA.md) |

Вывод: этот вид не теряется безвозвратно. Нужен только доступ к самим службам, то есть ваши учётные записи Telegram и DeepSeek.

### Вид В. Выдаются самим Supabase при создании проекта

| Что | Откуда берётся |
|---|---|
| Адрес проекта (`SUPABASE_URL`) | Страница проекта, раздел ключей |
| Служебный ключ (`SUPABASE_SERVICE_ROLE_KEY`) | Там же |
| Открытый ключ (`SUPABASE_ANON_KEY`, публикуемый ключ) | Там же |

Вывод: у нового проекта они новые. Их не восстанавливают — их переносят в настройки функций нового проекта и в строку в приложении.

### Ваши собственные значения

`ADMIN_EMAIL` и `TOCHKA_ASSISTANT_OWNER_EMAIL` — ваш адрес почты. Это не секрет в обычном смысле, но без него кабинет администратора и управление ботом никого не признают владельцем.

**Порядок восстановления ключей.**

1. Открыть настройки функций нового проекта Supabase.
2. Вписать вид В — адрес и ключи нового проекта.
3. Вписать вид Б — ключ бота и ключ DeepSeek, полученные заново.
4. Вписать свой адрес почты в оба поля владельца.
5. Ключи вида А не вписывать: они приедут вместе с копией базы.
6. Выложить функции, затем заново привязать Telegram через приложение — это обновит закрытое слово и адрес обращения бота.
7. Проверить задания расписания: адрес проекта в них изменился, старый уже не отвечает.

## Часть 3. Загруженные файлы

**Что это.** Документы, которые люди прикрепляют в приложении: снимки, PDF, документы Word. Лежат в закрытом хранилище Supabase, в разделе `tochka-documents`, каждый в папке со своим номером человека.

**Важно понимать связь.** В базе хранятся только сведения о файле — название, размер, вид, путь. Сам файл лежит в хранилище отдельно. Восстановление базы без хранилища даст список документов, которые не открываются.

**Порядок восстановления.**

1. Восстановить базу — появится список документов.
2. Скопировать файлы в хранилище нового проекта, **сохранив пути без изменений**: имя папки должно остаться прежним номером человека, имя файла — прежним. Если путь изменится, запись в базе будет указывать в пустоту.
3. Проверить правила доступа к хранилищу — они создаются `supabase/rebuild.sql`, отдельно ничего настраивать не нужно.
4. Открыть в приложении один документ каждого человека. Если открывается — перенос верен.

## Проверка: что действительно сохранено сегодня

Проверено по исходному коду и документам проекта 16 сентября 2026 года. Личный кабинет Supabase владельца при этой проверке не открывался.

| Что | Сохранено? | Где |
|---|---|---|
| Структура базы, правила доступа, расписания | **Да** | В самом проекте: `supabase/rebuild.sql`, 16 источников, проверяется автоматически (`rebuild-regression.cjs`) |
| Ключи вида Б — бот, DeepSeek, выкладка | **Да, но не копией** | Выдаются заново сторонними службами по вашим учётным записям |
| Ключи вида А — подпись уведомлений, ключи расписаний, отпечаток Telegram | **Только вместе с копией базы** | Отдельного хранения нет |
| Записи людей — заметки, события, финансы | **Частично** | На устройстве каждого человека и в его файле резервной копии из раздела «Ещё». Общей копии всего облака нет |
| Учётные записи людей (`auth`) | **Нет** | Отдельной копии нет |
| Загруженные документы | **Нет** | Отдельной копии нет |

**Главный вывод проверки.** Весь порядок восстановления выше опирается на копию базы. Копии базы сейчас нет: на бесплатном тарифе Supabase автоматические ежедневные копии не делаются, а ручная выгрузка ни разу не снималась и нигде не хранится. То есть при потере проекта восстановить получится структуру, но не учётные записи, не документы и не общие данные облака.

Это не новая поломка, а то, что выяснилось при письменном разборе. Молчать об этом нельзя.

**Что это закрывает без платного тарифа.** Ручная выгрузка базы одной командой и копирование файлов хранилища — бесплатны. Их нужно снимать по расписанию и хранить там, где вы храните важные файлы. Это можно сделать двумя способами: делать вручную раз в неделю по короткой инструкции или настроить автоматическую выгрузку в GitHub по расписанию. Второй способ надёжнее — не зависит от памяти человека. Оба требуют вашего решения, поэтому ни один пока не сделан.

## Что делать вам

Решить, нужна ли регулярная копия облака, и каким способом: вручную раз в неделю по инструкции или автоматически по расписанию. Скажите — подготовлю выбранное. Пока решения нет, порядок восстановления выше остаётся написанным, но неподкреплённым: восстанавливать будет не из чего.
