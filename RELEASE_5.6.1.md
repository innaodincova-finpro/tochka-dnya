# Точка дня 5.6.1 — исправления по аудиту

Подготовлено из переданного архива 5.6. Изменения внесены в исходники; рабочий сайт и база в этой сессии не обновлялись.

## Что исправлено

1. Вместо безусловного upsert всей базы: чтение актуального снимка, объединение с последним подтверждённым состоянием и условный UPDATE по user_id + updated_at. При гонке запрос повторяется. Для нового аккаунта используется INSERT с обработкой одновременного создания строки.
2. Во время запроса новые локальные правки объединяются с подтверждёнными данными. При одновременной правке одного поля сохранение останавливается, в «Ещё» появляется выбор локальной или облачной версии. Перед выбором обе базы записываются в локальную аварийную копию. Независимые изменения объединяются.
3. Отправка разрешена только после успешного чтения аккаунта и проверки владельца локальных записей. Старые асинхронные ответы отсеиваются номером подключения. При смене аккаунта предыдущие записи откладываются отдельно по его ID; при возвращении они подхватываются.
4. Слияние вкладок не генерирует новое время сохранения. Порядок записей стабилизирован, события другого владельца игнорируются.
5. Добавлена форма нового пароля, проверка повторного ввода, обработка PASSWORD_RECOVERY и updateUser. Отправка настоящего письма и разрешённый redirect URL требуют проверки на опубликованном адресе.
6. Проверяются даты, записи, суммы, списки, идентификаторы и структура перед импортом или загрузкой из облака. Некорректная локальная база блокирует перезапись; её исходные байты можно скачать через «Ещё». Перед импортом сохраняется локальная копия предыдущего состояния. Отсутствующие после восстановления записи получают отметки удаления.
7. Календарь: событие без времени получает напоминание за 15 часов, то есть накануне в 09:00 относительно начала дня.
8. Кэш обновлён до 5.6.1; очистка затрагивает только кэши «Точки дня», ошибочные HTTP-ответы не записываются в кэш.
9. Добавлена серверная защита от старого протокола записи. Клиент передаёт версию в стандартном x-client-info; триггер блокирует старые INSERT/UPDATE от роли authenticated. Это защита совместимости клиентов, а не замена RLS.

## Проверено

- `npm ci --no-audit --no-fund` — установка из lock-файла.
- `npm test` — 393 проверки существующего набора, 17 новых регрессионных проверок, проверки SQL и внутренних ссылок.
- SQL выполнен в локальном PostgreSQL через PGlite: старый INSERT/UPDATE отклоняется, новый разрешён; SELECT и UPDATE чужой строки запрещены RLS.
- Все данные проверок искусственные. Существующий Supabase-проект не использовался для тестовых записей.

Старые тесты клиента обновлены под условный UPDATE вместо upsert. Тестовые списки теперь содержат обязательную дату. Проверки прежних пользовательских возможностей сохранены.

## Что НЕ подтверждено

iPhone/Safari, установка и обновление PWA, доставка письма, переход из письма на опубликованный сайт, фактические настройки и права рабочей базы, обновление календарной подписки iOS. Браузерная приёмка выполнена позднее через управляемый preview; фактические результаты приведены в BROWSER_ACCEPTANCE_5.6.1.md. Настоящий iPhone не проверен.

## Порядок выпуска для исполнителя

1. Создать ветку и PR из этого пакета в нужном репозитории. Исходный архив 5.6 сохранить отдельно. Не заменять рабочую базу содержимым архива.
2. На отдельной тестовой базе применить `supabase/DATABASE_SETUP.sql` (он включает защиту), выложить функции и приложение. Для существующей базы достаточно `supabase/DATABASE_SYNC_GUARD.sql`.
3. Проверить сценарии из следующего раздела на тестовых аккаунтах. До приёмки оставить PR черновиком. CI запускает `npm ci` и `npm test`.
4. Перед рабочим выпуском сделать серверную резервную копию и локальные копии на устройствах с неотправленными записями. Новая версия не умеет восстановить записи, уже потерянные до обновления.
5. Применить `DATABASE_SYNC_GUARD.sql` к рабочей базе в согласованном окне обновления, затем выложить 5.6.1 и обновлённую функцию `kalendar`. Между этими шагами старая версия получает ошибку облака, локальные данные остаются. Без серверной защиты старые вкладки всё ещё могут перезаписать новые данные.
6. Обновить приложение на устройствах. Не очищать данные браузера и не удалять PWA при наличии неотправленных записей. Подтвердить синхронизацию и доступ со второго устройства.
7. При проблемах приостановить выпуск. Откат одного HTML к 5.6 оставит запись в облако заблокированной защитой — это ожидаемо. Не снимать защиту только ради возврата старого небезопасного сохранения.

Эти шаги предназначены для исполнителя выпуска: пользователю не нужно вручную менять фрагменты HTML.

## Приёмка на тестовых аккаунтах

- На двух устройствах одного аккаунта добавить разные записи; проверить сохранность обеих после обновления страницы и повторного входа.
- Одновременно изменить одно поле. Открыть «Ещё», выбрать каждую из версий в отдельных прогонах; проверить сохранение независимых изменений и аварийной копии.
- Изменить запись во время медленного запроса, одновременно добавить другую запись на втором устройстве. Обе должны сохраниться.
- Прервать чтение при смене А → Б, затем изменить локальную запись. В облако Б не должно попасть содержимое А.
- Открыть две вкладки, проверить добавление/удаление и отсутствие бесконечного обмена записями.
- Загрузить некорректную копию: текущая база должна остаться прежней. Проверить корректное восстановление и локальную копию до восстановления.
- Пройти настоящее письмо «Забыли пароль?» до формы нового пароля; выйти и войти с новым паролем.
- Проверить все разделы и новые формы на ширине 375 px и на iPhone, светлую/тёмную тему, клавиатуру и прокрутку.
- После успешного онлайн-запуска открыть приложение без сети, внести запись, вернуть сеть и подтвердить её появление на втором устройстве.
- Проверить календарную подписку: событие без времени, накануне 09:00; учитывать собственные настройки уведомлений iOS.

## Ограничения решения

Облако по-прежнему хранит один JSON-снимок на аккаунт. Новая версия защищает запись оптимистическим контролем и объединением; это не серверная история всех изменений. При редактировании одного списка на двух устройствах может потребоваться выбор версии списка. Сведения о последнем подтверждённом снимке хранятся локально по аккаунту. Если локальная история отсутствует и версии различаются, приложение может запросить выбор вместо автоматического угадывания. Работа без локального хранилища не считается безопасной. Аварийные копии на устройстве не заменяют серверное резервирование.
